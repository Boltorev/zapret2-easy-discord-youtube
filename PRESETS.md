# Пресеты «Запрет2 Easy»

Пресет — это файл `presets\<ИМЯ>.txt`, который описывает набор профилей обработки
трафика для движка zapret2 (`winws2.exe`). Запускаются все пресеты одинаково:
меню → «Установить» → выбрать пресет.

Формат файла описан в `presets\_FORMAT.md`.

---

## Как выбрать пресет

1. Начните с **AUTO** — он сам переключает стратегии, если сайт не открывается.
2. Если AUTO не помог — откройте **«Тесты пресетов»** (п.5 меню): он прогонит все
   пресеты и покажет, какие цели открываются у каждого.
3. Выберите пресет с лучшим результатом и поставьте его.

Никто не знает заранее, что работает у вашего провайдера: DPI везде разный.
Поэтому перебор — нормальная практика, а не признак поломки.

## Пресет AUTO — как он работает

AUTO — единственный пресет, который **сам меняет стратегию**, если сайт перестал
открываться. Это не «магия»: движок считает неудачи по конкретному хосту и
переключает номер стратегии.

### Четыре независимых домена ротации

| Домен | Профиль | `key` | Что покрывает |
|---|---|---|---|
| YouTube | `yt-tls` | `yt` | TCP 443, TLS, `list-youtube.txt` |
| Discord | `discord-tls` | `dc` | TCP 443, TLS, домены Discord |
| Общий | `common-tls-http` | `cm` | TCP 80/443, TLS+HTTP, `list-general.txt` |
| QUIC | `quic` | `qc` | UDP 443, QUIC |

Плюс `discord-udp` (media/voice) — **без** ротации, см. ниже.

Состояние ротации лежит в `autostate.<key>.<домен 2-го уровня>`. Разные `key` —
разные хранилища, поэтому **отвал YouTube не трогает Discord**: у них разные
счётчики неудач. `nld=2` означает, что все `*.googlevideo.com` считаются одним
хостом, а не десятком разных.

Порядок профилей важен: профиль выбирается по первому совпадению, поэтому узкие
хостлисты (YouTube, Discord) стоят раньше общего.

### Кандидаты — от минимального вмешательства к максимальному

| strategy | Техника | Взято из | Проверено |
|---|---|---|---|
| 1 | fake + multisplit с seqovl | `FAKE-TLS-AUTO-ALT2` | да (2/2) |
| 2 | hostfakesplit | `ALT9` | да (2/2) |
| 3 | fake + fakedsplit | `ALT1` | да (2/2) |
| 4 (`final`) | fake-набор + multidisorder + подмена SNI | `FAKE-TLS-AUTO` | да (2/2) |

seqovl первым — потому что не требует «доверия» сервера: тот принимает только часть
сегмента за счёт sequence numbers. Последняя стратегия помечена `final`: когда
ротация доходит до неё, переключения прекращаются, и AUTO остаётся на ней.

Для QUIC кандидатов три: `fake repeats=6`, `fake repeats=11`,
`fake + ipfrag(32) + drop` (`final`). **Они не проверены** — UDP-трафик в тестах
не упражнялся.

### Пороги

`fails=4`, `time=45`, `retrans=3`, `maxseq=32768`, `inseq=4096`, `nld=2`;
для QUIC дополнительно `udp_out=3`, `udp_in=1`.

- `fails=4` — одна неудача засчитывается не более одного раза на соединение,
  значит 4 = четыре разных неудачных соединения. Дефолтные 3 склонны к дёрганью.
- `time=45` (меньше дефолтных 60) — счётчик «затухает» быстрее, ротация отражает
  текущую проблему, а не накопленную за минуту.
- `reset` намеренно **не задан**: RST ретрансмиттеру рвёт соединение пользователю
  и создаёт шум.

### Диапазоны — в байтах, не в пакетах

```
--out-range=-s34228     # 32768 + 1460
--in-range=-s5556       # 4096 + 1460
--lua-desync=circular:...
--in-range=x
```

Пакетный режим здесь неприменим: `-d10` отсекает вызовы Lua примерно на 14.6 КБ,
и блокировка DPI на пороге **16 КБ** оказалась бы за границей диапазона —
детектор ретрансмиссий её просто не увидит.

Для UDP-профиля используются `--out-range=a --in-range=a`: режим `s` — это TCP
relative sequence, для UDP он не определён. Объём ограничен сигнатурными
фильтрами WinDivert, а не диапазонами.

### Почему у Discord voice нет ротации

У UDP-медиа нет надёжного сигнала неудачи: детектор считает только перехваченные
пакеты, а сервер может молчать по естественным причинам. Слепая ротация там
скорее навредит, поэтому стратегия фиксированная (`repeats=6`).

### Статические ipset-профили

Два профиля (`ipset-tls`, `ipset-quic`) включаются **только** при включённом
IPSet Filter — они помечены `--easy-require=ipset`. По умолчанию неактивны:
33 048 записей в память не читаются. Стоят последними, чтобы хостлистовые
профили выигрывали по приоритету.

### Как убедиться, что ротация работает

Ротация **проверяется в бою, а не синтетикой**: чтобы сработал детектор неудачи,
нужны реальные неудачные соединения. В тестовом прогоне все соединения прошли
с первой попытки, поэтому события переключения не появились — это нормальный
результат, а не отсутствие функции.

Маркеры для поиска в логе движка (`logs\winws2-AUTO.log`, включается `--debug`):

| Строка в логе | Что означает |
|---|---|
| `circular: start from strategy 1` | оркестратор стартовал |
| `circular: current strategy N` | какая стратегия применяется сейчас |
| `circular: rotate strategy to N` | **произошла смена стратегии** |
| `circular: final strategy N reached. will rotate no more.` | дошли до последней |
| `automate: host record key 'autostate.yt.…'` | к какому домену привязано состояние |
| `standard_failure_detector: retransmission 2/3` | причина неудачи — ретрансмиссии |
| `standard_failure_detector: incoming RST s…` | причина неудачи — RST от DPI |

Проверка «крутится ли ротация» по конкретному домену:

```
findstr /C:"rotate strategy" logs\winws2-AUTO.log
findstr /C:"autostate.yt" logs\winws2-AUTO.log
```

Если этих строк нет, а сайт не открывается — значит соединения вообще не
доходили до движка (см. раздел про `NO_TRAFFIC` в отчётах тестов).

## Отклонения от оригинальных пресетов Flowseal (осознанные)

### 1. `cutoff=nN` переведён в `--out-range=-dN`, а не `-nN`

Flowseal задаёт отсечение счётчиком пакетов `n`. В winws2 по умолчанию включён
`--wf-tcp-empty=0`: пустые ACK-пакеты **не перехватываются**, поэтому счётчик `n`
показывает не реальное число пакетов в соединении. Это прямо описано в `manual.md`
(раздел «Внутрипрофильные фильтры», предупреждение про `--wf-tcp-empty=0`).
Счётчик `d` (пакеты с данными) работает корректно и не зависит от этой настройки.
Поэтому `n4` → `-d4`, `n3` → `-d3`.

### 2. Набор фейков: `repeats` — повторы КАЖДОГО фейка

В nfqws1 можно было указать несколько `--dpi-desync-fake-tls` — получался «набор».
Семантика `repeats` подтверждена help-текстом самого nfqws1
(строка в `winws.exe`): `--dpi-desync-repeats=<N> ; send every desync packet N times`,
то есть **каждый** desync-пакет отправляется N раз, а не весь набор N раз.

Поэтому в nfqws2 каждый блоб стал отдельным инстансом `fake`, и **каждый получает
полное значение `repeats`**. Например, `repeats=11` на два блоба → 11 + 11 пакетов
(а не 6 + 5, как было в первой версии генератора).

Следствие: суммарный объём фейкового трафика выше, чем при трактовке «повтор набора».
Это не ломает обход (лишние фейки безвредны) и соответствует nfqws1.

### 3. `altorder=1` → `nofake1`

В nfqws2 у `fakedsplit`/`hostfakesplit` нет параметра `altorder`. Сам bol-van в
`docs/readme.md` (пример портирования `fakedsplit`) переводит `altorder=1` в `nofake1`.
Мы применили то же соответствие для `hostfakesplit` — это **приближение**, поведение
может отличаться от nfqws1. Отмечено здесь, чтобы не выглядело точным портом.

### 4. `--filter-l7=...,unknown` — фильтр снимается целиком

`unknown` — это тип **пейлоада**, а не протокол потока. Если оставить список
`discord,stun`, профиль перестал бы совпадать с потоками неизвестного протокола,
а nfqws1 их ловил (там был `filter-l7=unknown`). Поэтому при наличии `unknown`
фильтр `--filter-l7` убирается полностью — профиль ловит всё на своих портах,
а тип пейлоада отсекается через `--payload=unknown`.

### 5. Профили ipset и Game Filter — только при включённых фильтрах

В пресетах такие профили помечены build-директивой:

```
--easy-require=ipset
--easy-require=gamefilter
```

`core\Preset.ps1` вырезает эти токены и **выбрасывает профиль целиком**, если
соответствующий фильтр выключен. Поэтому:

- при `IPSet Filter = none` (по умолчанию) файл `lists\ipset-all.txt` не передаётся
  движку вообще — 33 048 записей не читаются;
- при `Game Filter = off` игровые профили не создаются, плейсхолдеры
  `{GAMEFILTERTCP}` / `{GAMEFILTERUDP}` вычищаются из списков портов.

Токены `--easy-*` **никогда** не попадают в аргументы `winws2` — это проверяется
ассертом в `core\test-runner.ps1`.

### 6. Тип профиля определяет, какие фейки в нём создаются

В nfqws1 `--dpi-desync-fake-tls` действует только на TLS-пейлоад, `--dpi-desync-fake-http` —
только на HTTP, `--dpi-desync-fake-quic` — только на QUIC. Один профиль мог нести
несколько типов сразу.

Генератор выводит **набор пейлоадов профиля** из его фильтров и создаёт фейки только
для них:

| Источник | Пейлоады |
|---|---|
| `--filter-l7=tls` | `tls_client_hello` |
| `--filter-l7=http` | `http_req` |
| `--filter-l7=quic` | `quic_initial` |
| `--filter-l7=discord` / `stun` | `discord_ip_discovery` / `stun` |
| `--filter-tcp` содержит 443 | `tls_client_hello` |
| `--filter-tcp` содержит 80 | `http_req` |
| `--filter-udp` содержит 443 | `quic_initial` |
| `--dpi-desync-any-protocol=1` | все известные + `unknown` |
| `--dpi-desync-fake-tls-mod=...` (нет других признаков) | `tls_client_hello` |
| явный блоб `--dpi-desync-fake-tls/http/quic/...` (нет других признаков) | соответствующий |

Если профиль пропускает TLS и HTTP (порты `80,443`), создаются **оба** фейка:
для TLS — из `--dpi-desync-fake-tls`, а если он не задан — дефолтный `fake_default_tls`
(ровно как делал nfqws1).

Отдельно: профили `discord.media` на нестандартных портах (`2053,2083,2087,2096,8443`)
не содержат ни 80/443, ни `filter-l7`, поэтому тип выводится из `--dpi-desync-fake-tls-mod`
или из явного блоба; если нет ни того ни другого — принимается TLS (это discord-медиа
поверх TLS) с пометкой в логе сборки.

Статический ассерт сборки: **каждый профиль обязан иметь хотя бы один инстанс,
соответствующий пейлоадам, которые он реально пропускает.** Иначе сборка падает.

Это важно понимать, чтобы не питать иллюзий.

Оркестратор `circular` умеет фиксировать два события:

- **неудача** — считается по исходящим ретрансмиссиям и по входящему RST;
- **удача** — по исходящему relative sequence (мы смогли отправить много) и
  по входящему relative sequence (сервер прислал много).

В нашей сборке **входящие TCP-данные не перехватываются**. Причина: конструктор
WinDivert автоматически перехватывает только входящие `SYN+ACK`, `FIN` и `RST`
(см. `manual.md`, раздел про перехват в Windows). Полный `--wf-tcp-in=443` мы
сознательно не включаем: это прогон всего входящего видеопотока через userspace.

Следствия:

- детектор неудачи **работает полностью**: ретрансмиссии — по исходящим,
  RST — по автоматически перехваченным входящим;
- детектор удачи по **исходящему** sequence работает;
- детектор удачи по **входящему** `inseq` (порог 4096) **не срабатывает никогда**,
  потому что входящие пакеты с данными до Lua просто не доходят.

То есть счётчик неудач в нашей конфигурации сбрасывается по факту успешной
отправки вверх и по истечении окна `time`, а **не** по факту получения данных
от сервера. Практический риск: на канале с потерями возможна ротация там, где
соединение на самом деле живое. Если такое будет наблюдаться — включается
`--wf-tcp-in` (дороже по CPU) или ставится более консервативный `fails`.

Параметр `--in-range=-s5556` в AUTO всё равно задаётся: он бесплатен и нужен,
чтобы `circular` видел автоматически перехваченный входящий RST.

## Плейсхолдеры и настройки

В файлах пресетов встречаются:

| Плейсхолдер | Откуда берётся |
|---|---|
| `{ROOT}` | папка сборки, подставляется `Preset.ps1` |
| `{GAMEFILTERTCP}` | `easy.settings.json` → `GameFilterTCP` |
| `{GAMEFILTERUDP}` | `easy.settings.json` → `GameFilterUDP` |

Файл настроек `easy.settings.json` создаётся меню:

```json
{
  "Preset": "AUTO",
  "IPSetFilter": false,
  "GameFilter": false,
  "GameFilterTCP": "",
  "GameFilterUDP": ""
}
```

Значения по умолчанию: **IPSet Filter выключен, Game Filter выключен.**
